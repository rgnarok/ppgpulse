## 2. Dynamic user management

### Create users (Roles & Access)

A **Create user** form was added to the **Roles & Access** page. It captures:

- **Name**
- **Email**
- **Team** (defaults to `PPG`)
- **Auto-generated password** — strong, shown once after creation with a
  *Copy credentials* button, and a ↻ button to regenerate before submitting
- **Type = `user`** (a new base role)
- **Section access** — checkboxes to select/deselect which sections the person
  can see (Home, Interviews, HDIS, My Team, Profile are pre-checked; Users,
  Roles & Access, Team Hierarchy are available too)

New accounts appear in **Users** immediately and report to whoever created them,
so the **Team Hierarchy** grows automatically.

**How access works:** the `user` role has only *Profile view* by default. Each
section you tick is granted to that specific person as a per-user override
(role permissions ∪ overrides). Unticking a section simply doesn't grant it.

### Remove users (Users page)

Each row in **Users** has a **Remove** action.

- Super-admin rows stay locked for HR Managers.
- You cannot delete your own account.
- Removing a user permanently deletes the account and any data linked to it.

### Durable clean state (important)

Production boot now ensures **only roles + the super-admin account** — it no
longer re-seeds the demo dataset on every restart. This means **accounts you
delete in the UI stay deleted** across redeploys/restarts.

> To clean your currently-live site: log in as Kushagra → **Users** → **Remove**
> the demo accounts. They will not come back. Removing the demo consultants also
> clears their linked requirements (empties the Home/report demo data), which is
> the intended "clean start". The 138 demo HDIS records are not tied to users, so
> they remain unless deleted from the HDIS screen.

Full demo data is still available for local development and the test suite via
`npm run seed`.

## 3. Interviews — rich details + daily table

### Expanded add form (for anyone with interview edit access, e.g. consultants)

| Field | Example | Notes |
|-------|---------|-------|
| Interview update | `2026090701` | reference/update code |
| Round | `L1` | dropdown L0–L5 |
| Candidate | `RAGINI SANKHWAR` | full name |
| Email | `ragini17mar@gmail.com` | candidate email |
| Time | `12:30 PM` | free text |
| Profile | `Sr. People Consultant` | role interviewed for |
| With | `Priya Pal` | interviewer name |
| Sourcing (PPG) | `Vanya Parihar` | **auto-defaults** to the logged-in consultant running the interview; can be changed |
| Session | Mid-day / End-day | kept from the existing calendar model |
| Status | `Scheduled / Selected / Rejected / On Hold` | dropdown |

### Daily details table

Clicking a day on the calendar opens a **table of every interview for that day**
with columns: Interview (ref + round), Candidate (+ email), Time, Profile, With,
Sourcing, Status.

- **Visibility follows access.** Org-scope users (admins) see all interviews;
  team/own-scope users see only their in-scope rows.
- **Status is editable inline** — change it right in the table and it saves
  immediately. Read-only users see status as a coloured pill instead.
- Edit users also get a **Remove** action per row.

The new interview fields are **nullable columns** added automatically by
`prisma db push` on boot — a safe, non-destructive schema change (no data loss).

## Deployment

1. On Render → your web service → **Manual Deploy → Deploy latest commit**
   (latest commit on `claude/new-session-pl28c4`).
2. On boot the server:
   - runs `prisma db push` (adds the new interview columns),
   - ensures roles + the super-admin account,
   - logs `Baseline ready: {"roles":4,"admins":1}` on success (confirms the DB
     is reachable and seeded).
3. Sign in with `kushagra@vayuz.com` / `Passw0rd!` (or your `SUPER_ADMIN_PASSWORD`).
